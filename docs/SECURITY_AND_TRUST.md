# Security and trust

Java modules execute with the game's JVM permissions. KnoxBridge is not a Java sandbox. Approval informs the player and keys trust to the actual JAR's SHA-256 digest; it cannot make malicious Java code safe.

The Windows setup verifies the embedded player archive and its bundled runtime JAR/bootstrap DLL against included SHA-256 sidecars before installation. These checks detect accidental corruption or inconsistent package contents; they are not a code-signing certificate, publisher authentication, malware scan, or guarantee that Windows Security will accept an unsigned installer. Stop if antivirus reports a threat. Do not restore, run, or whitelist a flagged file.

Unknown and changed JAR hashes are blocked by default. The Bridge Workshop Lua screen displays JARs found beneath enabled PZ mod roots and collects exact-hash allow/deny choices in the user's `Zomboid/Lua/KnoxBridge` directory. On the next full launch, the Java agent imports once-only or remembered decisions into `%USERPROFILE%\Zomboid\KnoxBridge\trust.properties` before checking modules. If the list or decision file is missing or invalid, unknown JARs stay blocked. A changed binary has a different hash and requires a new decision.

The screen displays module name and declared `author` from `mod.info` as unverified claims, plus module ID, version, and full JAR SHA-256. The selected row is highlighted, the details identify the selected JAR, and Allow/Deny actions apply to that selection. It shows unsupported enabled-mod JARs too; those remain blocked and cannot be allowed until the author adds a valid KnoxBridge descriptor/API entry point. The full-screen gate appears at the PZ main menu before world entry. Decisions apply on the next launch because Bridge discovery/loading happens before PZ's Lua main-menu UI, and late module loading can miss required early instrumentation targets.

**Remember next choice** applies only to the next successfully saved decision, then resets. Without it, the queued choice applies for one PZ launch to that exact hash (including any enabled modules with the same JAR hash); the next launch resumes the previous remembered decision, if one existed. A remembered choice persists for that exact hash until the JAR changes or the player changes the choice. A restart is needed only when the effective loaded module set changes. The player must confirm quitting to desktop, then start PZ again through Steam; KnoxBridge does not automatically relaunch the game. If the review UI or file handoff fails, unknown modules remain blocked; report the issue rather than bypassing it. These screen and restart interactions still need live Build 42 testing. Never distribute private signing keys in this project or a module.

### Detached digital signatures

Publisher signatures are a separate trust layer from SHA-256 approval. A hash answers “are these the exact bytes I approved?” A valid digital signature can answer “was this artifact signed by the holder of this public key, and have the signed bytes changed?” Neither answer proves that the code is safe, and a signature alone does not make an author trustworthy.

The source candidate now implements detached Ed25519 signatures using the JDK cryptography provider. Each module may ship `<declared-jar-filename>.knoxsig` beside its JAR. The signature covers the module ID, version, API version, entrypoint, class-loader policy, normalized relative JAR path, filename and exact JAR SHA-256. A malformed, unsupported, or mismatched present sidecar blocks that module even if its hash was previously allowed. Missing sidecars retain the existing unsigned exact-hash approval policy. The runtime loads a temporary copy checked against that same approved hash, preventing an ordinary source-file change between verification and class loading from substituting a different JAR.

The screen shows the full public-key SHA-256 fingerprint separately from the declared author. **Valid signature** means those bytes were signed with that key; compare the fingerprint with a publisher's independently trusted channel. It does not authenticate the bundled name. Signatures never automatically allow modules or updates. Each changed JAR still needs approval. Removing a sidecar makes a module unsigned; the runtime does not pin a previously observed signer or require all mods to be signed. Download verification with an expected fingerprint rejects unsigned files and wrong signers.

The sidecar contains exactly four LF-separated lines: `KnoxBridge-Ed25519-v1`, Base64 X.509 encoded Ed25519 public key, Base64 64-byte signature, and an empty final line. Extra fields, unsupported versions, nonregular/symlink sidecars, and files over 1024 bytes are rejected. Signed payloads use big-endian 32-bit length-prefixed UTF-8 strings: domain `KnoxBridge detached signature v1`, basename, lowercase SHA-256, then a 32-bit context-field count and each context string. Module context fields are `module`, ID, version, API version, entrypoint, loader policy, relative JAR path (forward slashes). File context has one field, `file`. This avoids delimiter ambiguity and cross-use of release and module signatures.

### Author and release workflow

Build the runtime first (`gradlew :runtime-core:jar`). Run the offline tool with `java -cp <agent.jar> com.knoxbridge.runtime.SigningTool` followed by one command:

- `keygen <private.pk8> <public.der>` creates a key pair at new paths. The PKCS#8 private key is **unencrypted**: keep it outside the repo/mod/release tree with restricted filesystem access and an offline backup. Publish only the public key/fingerprint. Output files are never overwritten.
- `sign-module <selected-mod-root> <private.pk8> <public.der>` signs the built descriptor/JAR. Ship the sidecar beside the JAR; sign after final metadata/build changes. Existing sidecars are never overwritten: remove a stale one deliberately before signing a new build.
- `verify-module <selected-mod-root> <expected-public-key-fingerprint>` verifies the signature against a fingerprint obtained independently.
- `sign-file <artifact> <private.pk8> <public.der>` signs any final ZIP, JAR, DLL, or EXE; distribute its `.knoxsig` too. Signing the final ZIP binds all files it contains. This is detached verification, not Windows Authenticode or automatic installer verification.
- `verify-file <artifact> <expected-public-key-fingerprint>` rejects changed, unsigned, or differently signed downloads.

Keep one publisher key stable across builds. Rotation or key loss produces a different fingerprint: announce the replacement through a trusted channel and have users compare it again. No automatic key migration, revocation feed, timestamp/freshness proof, rollback protection, or publisher-wide approval is implemented. A compromised key must be treated as compromised even when its signatures verify. Existing exact-hash denies remain available. Do not introduce publisher-wide auto-approval without a separately agreed key-trust/revocation policy.

The alpha11 runtime anchors the `.exe` publisher identity to public-key SHA-256 `eda1c49f4f51e604d86c1889fe72f90f16c42ff7bb6c69f1d9be74d79645228f`. The public key is distributed in `security/publisher-public.der`; no private key is included. A valid module signature from this key displays **Verified publisher: .exe**. Declared author text alone cannot establish this identity. Other authors may sign immediately with their own keys; unknown keys show a valid signature and fingerprint for independent comparison. Adding another recognized name requires the Bridge maintainer to verify the author's key through an independent channel and review a runtime registry update. There is no self-service identity proof or automatic publisher-wide approval.

For the owner, `scripts/initialize-publisher.ps1` creates a stable key outside the repository, restricts its directory to the current Windows account, and stores the private key encrypted with Windows DPAPI CurrentUser. `scripts/sign-release.ps1 -Artifacts <final-artifact-paths>` decrypts only into that restricted directory while signing, verifies every result, and removes the temporary plaintext key in its finally block. Reusing an existing sidecar verifies it rather than replacing it. DPAPI ciphertext is tied to this Windows account: copying it alone to another computer is not a portable backup. Preserve the Windows account recovery material and arrange a secure offline key backup before reinstalling Windows; never commit or publish the private key. The public fingerprint remains stable across releases.

Detached `.knoxsig` files do not provide Windows Authenticode certification or change Windows' unknown-publisher prompt. Publish the final EXE/ZIP sidecars with the downloads and publish the fingerprint independently. Older agents ignore detached module sidecars; enforcement and recognized-publisher display require alpha11. Existing unsigned KnoxSurvivors remains compatible and does not require an update. It will acquire verified publisher display only when a future mod release includes its own module signature.

For a signed owner release, run verification and checksum generation first; sign the final runtime JAR, API JAR and bootstrap DLL; then package with `gradlew packageManualInstaller buildWindowsInstaller packageRuntime -x buildWindowsBootstrap -x writeChecksums` to preserve those exact signed inputs. Sign the final player ZIP, developer ZIP and EXE last. A native bootstrap rebuild changes its bytes and requires fresh checksums/signatures; never reuse stale sidecars. Verify all outer and embedded signatures before publication.
