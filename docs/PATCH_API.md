# Patch API

Modules register a patch ID, target class, method name, optional JVM descriptor, required/optional flag and byte transformer. Patches are attached to their registering module for diagnostics. Duplicate patch IDs or identical targets are rejected. Register patches during `initialize` through `context.patches()`.

At class definition, a small class-file reader enumerates methods; already-loaded registered targets may also be retransformed after module startup if the JVM supports it. `className` uses dotted Java names (for example, `zombie.SomeClass`), not a slash-separated class-file path. A JVM descriptor identifies the exact method signature, for example `()Ljava/lang/String;`; use the target game's actual method descriptor. A named target is accepted only when exactly one method matches; when a descriptor is present, it must match exactly. Missing or overloaded descriptor-less targets log an incompatibility and are skipped. The runtime never falls back to a guessed overload.

The transformer receives the class name and original class-file bytes. It must return valid class-file bytes (return the input unchanged for a deliberate no-op). A thrown exception or invalid output is logged against the owning module and that transformation is not applied; this does not by itself abort PZ. Duplicate targets and mismatches are diagnostic failures, not rollback of other successful patches. Patches run as trusted Java code with the game's permissions.

The current core does not provide a bytecode advice library, parameter-supertype matching, alternative descriptors, patch dependency negotiation, retransformation reconciliation, or required-patch module blocking. Module authors provide the actual byte transform and are responsible for returning valid class bytes. `required` is currently diagnostic metadata only: a missing/failed required patch does not block the module or game startup. Do not treat it as an enforcement guarantee.

The independent `test-module` source registers a harmless no-op probe against its own fixture class. That verifies API wiring only; it is not a supported PZ patch example. Start with a no-op or isolated fixture, inspect exact target signatures in the target PZ build, and live-test real transformations in a disposable game profile.
